## 背景

我日常的信息入口基本就是微信：看到一段话、一篇文章、一个链接，转发给"文件传输助手"就算存下来了。
但存下来之后**再也没打开过**。

想要的是：转发那一刻就自动变成一条结构化的笔记，落进 Obsidian，将来能搜到、能双链。

## 方案

三个组件，各干一件事：

```
微信转发
  → 服务端（Node）：接消息、调模型整理成 Markdown
  → 飞牛 NAS：存文件（家里常开，天然做中转）
  → Obsidian 插件：定时拉取，写进 vault
```

几个设计取舍：

- **不做多端同步**：Obsidian 自己已经有同步方案，插件只负责"从 NAS 取"
- **AI 只做整理不做总结**：把"这段话在讲什么"整理成标题、要点、标签，但不替我下结论
- **一切落成纯 Markdown**：不引入数据库，将来换个工具也不用迁移

## 过程

服务端收到的原始内容很脏：可能是纯文本、可能是 HTML 片段、可能只有个链接。
先做一层清洗，再喂给模型，要求输出固定结构：

```markdown
---
title: 自动生成的标题
tags: [标签1, 标签2]
source: 转发来源
date: 2026-09-15
---
正文（保持原意，只做分段和要点化）
```

插件那边就两个动作：拉清单、下载新文件。

## 踩坑

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| 转发图片时笔记里只有一个占位符 | 图片存在微信侧，服务端拿不到原图 | 只处理文字和链接，图片明确的场景手动补 |
| 生成的标题经常一模一样 | 模型对短文本倾向套模板 | 提示词里强制"标题必须包含具体对象"，并做去重校验 |
| NAS 上跑起来路径全错 | 部署包用了开发机的绝对路径 | 改成从环境变量读，`.env.example` 里写清楚 |
| 插件偶尔重复导入 | 拉取时只看文件名不看内容，重名会覆盖 | 用内容哈希命名，导入前比对 |

## 结果

**能用，但停在"暂停"。**

- 服务端和插件的链路是通的，能生成结构化的 Markdown
- 打成 NAS 部署包（含一键脚本），理论上换台机器能直接装
- 但这套东西后来没在我主力机上继续跑

诚实说：**这个项目的真实价值没有被验证**。因为我转发的内容本身很零散，AI 整理出来还是一堆零散的笔记，
"能自动入库"解决了搬运问题，没解决"以后会不会看"的问题。

## 复盘

- 自动化的价值在于**减少摩擦**，但如果内容本身没有整理标准，自动入库只是把垃圾搬了个地方
- 组件越多（服务端 / NAS / 插件），任何一环出问题就整条链断，维护成本被低估了
- 如果重做：先只做"转发 → 一条 Markdown 丢进 inbox 目录"，不做 AI 整理，跑一个月看看到底有没有用
