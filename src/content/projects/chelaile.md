## 背景

「车来了」是个实时公交 App，我实际只想要一个功能：**广州的公交车现在到哪了、还有多久到站**。

官方 App 广告多、要登录、要开定位权限。想法很朴素——能不能只取那一小块数据，塞进自己的页面里。

## 方案

正常会走三条路，先按成本从低到高排：

1. **看官方网页版有没有现成接口**（成本最低，先试这个）
2. 官方/政府开放数据平台
3. 商业数据接口

我从第 1 条开始：把车来了 H5 落地页的产物拉下来，看它到底怎么跟服务端通信。

## 过程

官方页面只加载三个脚本：

```
index.html
├── cll-md-1.0.1.js     30KB   自研埋点 SDK
├── chunk-vendors.js   102KB   框架 + 依赖
└── app.js              21KB   业务代码
```

逐个读下来，结论很干脆：

- **`app.js` 是"下载落地页"**，通篇是 `navigator.userAgent` 分流 + 跳应用商店，整份文件里出现的域名只有 CDN、下载站和 `itunes.apple.com`
- **没有任何业务 API 调用**，也没有 `secret` / `sign` 这类签名字段
- `cll-md.js` 是自研埋点 SDK，用 1×1 图片 beacon 把事件打到日志域名，字段白名单里**确实有 `secret/sign/imei/mac`**——但那只是"上报时顺手带上"，签名逻辑不在里面

顺手记了两条事实：

- 应用包名有三个变体（标准版 / 大字版 / 鸿蒙版），深链能直接拉起 App
- 下载链路是 302 跳到 APK，包有 78MB，混淆过——静态分析成本远高于收益

所以第 1 条路直接堵死：**网页端不承载业务接口，签名要么在 App 原生层，要么在服务端做。**

## 转折

社区里已经有现成的开源实现把签名和响应解密都做掉了（MD5 签名 + AES 解密，免登录、不需要 key）。

拿它验证了一下，数据是真的：城市 ID、站点下的线路、在途车辆、到站倒计时都能拿到。
**既然路已经有人铺好，就没必要自己去反编译 78MB 的 APK。**

## 第一版：挂在 NAS 上

最先的版本是 Nuxt 跑在家里那台飞牛 NAS 上，Cloudflare 回源——能用，也用了半个月。

但它有个隐患：**出门在外，能不能查到车取决于家里那台机器**。断电、重启、宽带抽风、系统更新，
任何一个环节出问题，页面上就是 522。出门前想看车却发现打不开，这种事发生一次就够了。

## 第二版：搬到 Cloudflare 全托管

改造思路和我的个人站一样：**Astro 静态页 + Cloudflare Pages + GitHub 自动部署**，成本 0。

难点只有一个：**签名和解密必须放在服务端**，不能放浏览器（会暴露算法，也有跨域问题）。
Cloudflare Pages 的边缘函数正好接住这一层：

```
浏览器 ──GET /api/nearby?lat&lng──▶ Pages Function
                                      ├─ MD5 签名
                                      ├─ 请求 web.chelaile.net.cn
                                      └─ AES-256-ECB 解密，整理成精简 JSON
```

中间这一段比想象中麻烦，两个坑：

**一、WebCrypto 里没有 MD5**

这倒好办，纯 JS 实现一个，和 `node:crypto` 对拍 7 组（含中文、长串、空串）全一致。

**二、WebCrypto 里也没有 AES-ECB**

这个才是真卡点。WebCrypto 只给 CBC / CTR / GCM，而 **CBC 会校验 PKCS#7 填充**——
拿它去解 ECB 密文，最后一块必然对不上，直接抛 `OperationError`。

试过把整段密文丢给 CBC 零 IV 解密再用前一个密文块 XOR 还原，思路是对的，但填充校验先报错，
路走不通。最后老老实实写了个完整的 AES-256 解密（带密钥扩展），和 `node:crypto` 逐字节对拍 20 组，
在真实密文上解出了 110KB 的 JSON。

好消息是纯 JS 实现**不依赖任何运行时兼容层**，Workers 上直接跑通，不用担心环境差异。

## 踩坑

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| 一开始以为落地页里藏着接口 | 埋点字段里出现了 `secret`/`sign` | 分清"上报携带的字段"和"签名算法"，前者不含后者 |
| 想直接反编译 APK 拿算法 | 包 78MB 且混淆 | 成本太高，先找现成实现验证可行性 |
| AES 解密报 `OperationError` | WebCrypto 的 CBC 会校验填充，ECB 密文必然失败 | 自己实现 AES-256-ECB，逐字节对拍 |
| 签名正确但上游回 `status:400` | 上游校验客户端特征（UA / Referer / `xweb_xhr`） | 请求头必须和微信小程序一致，差一个都不行 |
| 换域名后访问 522 | DNS 改了但边缘还没认领这个域名 | 等两三分钟自动恢复，别急着改配置 |
| 接口可能随时变 | 未公开接口没有兼容承诺 | 只取最小字段、不做批量，失败了容易发现 |

## 结果

**跑通了，一直在用：[bus.wanyc.xyz](https://bus.wanyc.xyz)**

界面就一层，够用：

- **顶部**：城市 + 更新时间，每 30 秒自动刷新
- **站点卡片**：站名、距离，下面直接列线路和到站时间
- **每行线路**：到站倒计时（`15 分钟` / `即将到站`）、还有几站、运营时段；未发车的显示预计发车时刻（`17:25 发车`）
- 夜班车、短线、地铁换乘站都会单独标出来

现在的状态：

- Cloudflare Pages 托管，GitHub push 自动构建，**一分钟内上线**
- 边缘函数做签名和解密，浏览器只拿到精简后的 JSON
- 接口带 15 秒缓存，反复打开不会打上游
- 成本 0：静态页免费、函数免费额度远超个人用量
- 家里的 NAS 从此可以关掉，出门在外也不再依赖它

## 复盘

- **"官网看起来有接口"和"接口真的能被复用"是两件事**。先花一小时确认产物里到底有什么，比直接上手反编译省得多
- 这事最后不是我逆出来的——**认清"我要的是结果，不是过程"**，能直接用现成实现就别死磕
- **第一次落地选了最快的路（NAS），第二次才换成更稳的路（边缘）**。先用起来是对的，但别停在"能用"上
- 未公开接口最大的成本不是写代码，是**长期维护**：只取最小字段、不做批量、出问题能立刻发现
- 平台能力有缺口时（MD5 / ECB），**自己实现往往比绕路更快**——前提是能对拍验证

## 合规说明

只做**只读、低频**的「附近站点」查询，不做批量采集、不转售数据、页面设了 `noindex` 不被搜索引擎收录。

签名与解密用到了社区开源项目已公开的常量和算法，实现放在自己的仓库里；上游一旦改签名就会失效，
届时优先去看上游参数有没有变。真要长期稳定使用，走开放数据或买接口更省心。
